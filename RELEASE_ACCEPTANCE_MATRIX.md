- Identity blocker: Flutter obtains and refreshes Directus session tokens and sends the access token to V2. The existing backend Directus verifier delegates token validity to `/users/me`, then queries active membership with the same caller token, maps tenant from that response, and fails closed; synthetic auth/API tests passed **49/49, exit 0**. It denies multiple active memberships absent a tenant-selection contract. Scalable Compose hardcodes OIDC and requires real issuer/audience/JWKS values. No production provider configuration was supplied. Options: (1) Directus pass-through validation is the least disruptive immediate fit, with an online Directus check and membership permission/single-membership policy; (2) a trusted exchange adds V2 issuer/key/refresh/revocation responsibilities; (3) shared OIDC is the cleanest long-term contract but requires Flutter/provider migration. Recommended immediate architecture is existing Directus verification only after operator approves Directus as V2 authority, its HTTPS endpoint/permissions, and the membership-selection policy. Do not accept client tenant/subject claims without checking membership server-side. AUTH-01/02, TEN-01 and FLU-01 remain PARTIAL; production identity/mobile release remain BLOCKED.
