## Package 2 final identity closure evidence (2026-10-20)

- Backend Directus mode calls `GET /users/me?fields=id,status` and then `GET /items/business_profile_members` with the user ID/status filters, four required fields, and `limit=2`, using the caller's bearer token for both. It derives `subject_id` from `/users/me` and tenant from the returned active membership. It does not read a tenant or subject from request payloads/headers for authorization. API media delete, upload, scan submit, status, results and labels use the verified principal tenant/subject. Synthetic backend tests cover expired/revoked token, inactive/missing/mismatched/ambiguous membership, permission denial, outage/429, cross-tenant access, and 12 concurrent independent identities (two upstream reads each).
- Directus policy must allow the caller to read their own `directus_users.id/status` and only the `business_profile_members` fields `id,user,business_profile,status`, with row-level restrictions to that user's active memberships (e.g. `user = $CURRENT_USER`, `status = active`). No write permissions or service token are needed for incoming-session validation. Exact policy/schema compatibility is installation-specific and remains unverified until isolated staging.
- Flutter's workspace selection supports multiple active organizations and persists a membership choice locally. Current V2 backend rejects multiple active memberships. The stored client choice is not trusted by the backend. Product owner decision and a server-verified membership-selection API contract are required before multi-organization employees can use V2.
- `deployment/staging/directus-auth.env.example` and `deployment/staging/DIRECTUS_AUTH_ACCEPTANCE.md` prepare placeholders and acceptance steps only. The scalable Compose manifest still hardcodes OIDC and requires OIDC interpolation; it is not switched, and no staging services, Directus instance, secrets, or production settings were changed. Real staging acceptance remains blocked on operator inputs and explicit approval for a staging-only Compose/service change.
- Directus mode currently performs two upstream identity reads per authenticated V2 API request with no positive authorization cache. This gives next-request revocation/membership visibility but makes Directus throughput and availability part of API capacity. No caching or load test was introduced without measured staging evidence and an approved revocation-delay policy.
